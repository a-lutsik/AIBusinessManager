# Этап 09 — канал Telegram и напоминания

Цель: клиент получает подтверждение и напоминания в Telegram, доставка фиксируется в журнале; клиенты без Telegram остаются на ручной задаче владельцу с готовым текстом.
Критерий готовности этапа:
1. Клиент привязывает Telegram по deep-link `t.me/<bot>?start=<одноразовый токен>`; `telegram_chat_id` записывается только после согласия, токен одноразовый, с TTL, в БД хранится хеш (как у токенов записи).
2. `TelegramNotificationChannel` отправляет через Bot API; результат пишется в `notification_delivery` (`SENT`, `FAILED` с причиной, `SKIPPED_NO_CHAT`). Блокировка бота клиентом (403) снимает привязку и переключает на ручной канал.
3. `BOOKING_CREATED` отправляет подтверждение клиенту в Telegram, без `chat_id` — ручная задача (`ManualTaskNotificationChannel`). Сейчас `BookingCreatedNotifyHandler` шлёт только в `telegram` и без `chat_id` пишет `STUBBED`.
4. Напоминания за сутки и за 2 часа до визита; идемпотентны (повторный запуск не дублирует), учитывают отмену и перенос, часовой пояс арендатора, локаль клиента.
5. Webhook бота: проверка `X-Telegram-Bot-Api-Secret-Token`, вне публичного лимита по IP не открывается, отвечает 200 на неизвестные апдейты.
6. Весь исходящий текст идёт из каталога сообщений по `preferred_locale` клиента; ПДн в логи не пишутся; токен бота только из окружения, в `prod` обязателен при включённом канале.
7. Регрессия зелёная: backend, фронтенд, `npm run e2e`, `npm run e2e:oidc`; Telegram в тестах — только stub HTTP-сервер.

Риск: HIGH (внешний субпроцессор получает имя и время визита, токены привязки, webhook из интернета).

Не входит: реактивация, возврат после неявки, поздравления, напоминание об остатке пакета (этап 11); `deductSession` при COMPLETED, Trust-override с аудитом (этап 11); Instagram (этап 10); живая проверка с реальным ботом и регистрация бота — шаг оператора.

## Решения
- Один бот на инсталляцию, не на арендатора (`APP_TELEGRAM_BOT_TOKEN`); арендатор определяется по токену привязки.
- Напоминания — `@Scheduled` + jOOQ по окну визитов, как outbox-поллер; Spring Integration и `notificationOutbound` не используются (канал-заглушка удалён), Batch не нужен.
- Согласие: привязка через бота = согласие на сервисные сообщения; маркетинговое (`marketing_consent`) отдельно и этим этапом не меняется.
- Подтверждение записи: без `chat_id`, при ошибке доставки и при отключённом канале — ручная задача (для публичной записи её роль играет `NEW_BOOKING`), сообщение не теряется. Напоминания — НЕ создают ручных задач: при выключенном канале задача напоминаний не запускается, клиентам без привязки напоминание не ставится в очередь, при сбое доставки напоминание теряется (журнал `FAILED`), владельца не шумим.
- Привязка доказывает владение номером: `/start <токен>` лишь связывает токен с чатом, бот просит поделиться своим контактом (`request_contact`); `chat_id` записывается, только если `contact.user_id` равен отправителю и номер контакта после нормализации равен `client.normalized_phone`. Токен гасится контактом в любом случае. Ссылка для публичной записи отдаётся одинаково, привязан клиент или нет (без оракула).
- Доставка не держит транзакцию во время вызова Telegram: исходящее сообщение ставится в очередь (`visit_message_dispatch`, PENDING), отдельный воркер (свой поток планировщика, `spring.task.scheduling.pool.size: 4`) берёт пачку (SENDING), коротко проверяет визит под `FOR SHARE` (статус и `service_start`), вызывает Telegram без транзакции, затем короткой транзакцией пишет журнал, снимает привязку на 403 (только этот `chat_id`), создаёт ручную задачу и ставит DONE. Остановка процесса возвращает сообщение в очередь; сообщение, зависшее в SENDING после падения, повторно не отправляется (исход неизвестен): FAILED и fallback.
