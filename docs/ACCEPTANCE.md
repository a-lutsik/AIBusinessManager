# Приёмка Cadence

Дата: 2026-11-01. Основа: коммит `abee64f` (этап 07) и незакоммиченные правки этапа 08 (`docs/stages/08-pilot-code-conditions.md`). Приёмка архитектора по политике, п. 4.3; заменяет версию после этапа 07. Объём — пилот с одним арендатором: веб-консоль и публичная запись; не весь план продукта (`docs/PRODUCT_PLAN.md`).

## Что реализовано и принято (этапы 01–08)
- Операционный срез (фазы 1A/1B плана): арендаторы с RLS, каталог услуг и мастеров с матрицей и графиком, движок записи (снапшоты, GiST-исключение, статусы), публичная запись `/book/{slug}` с `.ics` и ссылкой управления `/b/{id}?token=`, CRM из записи, роль MASTER без телефонов и денег, правила записи, светлая и тёмная темы, RU и EN, демо-сид (только вне профиля `prod`).
- Редактирование каталога из консоли (этап 07): услуги, мастера, матрица с переопределениями, недельный график, исключения; серверная валидация с кодами ошибок, аудит в `audit_log` без ПДн; удаления нет — только `active=false`/`publicVisible=false`; деактивированный мастер теряет консоль (403 `SPECIALIST_INACTIVE`), его визиты только отменяются.
- Условия пилота на стороне кода (этап 08): статический хост — сервис `web` в `docker-compose.prod.yml` (nginx без root, read-only, `127.0.0.1:8082`, правила и CSP в `docker/web/`), проверка маршрутов на настоящем nginx `scripts/web-host-check.sh` и job `web` в CI (TD-57); удаление данных клиента по запросу — `POST /api/app/clients/{id}/anonymize`, только OWNER, с необратимым подтверждением в карточке, одной транзакцией по CRM, визитам, ссылкам, задачам владельца, trust, пакетам и диалогам AI, включая профили, поглощённые при слиянии; факты визитов, журнал, счётчики и метрики прошлых периодов сохраняются; 409 при незавершённом визите и при повторе (TD-46, план §10); слоты консоли под авторизацией `GET /api/app/slots` вне публичного лимита по IP (TD-76); на `/book` ошибка слотов и 429 отличаются от «нет слотов» и дают повтор (TD-55); снапшот цены в панели визита владельцу, мастеру `null` (TD-71); запись каталога через настоящий токен Keycloak (E11-OIDC); блок «сегодня» по дню арендатора, без заглушки `METRICS_PENDING` (TD-82).
- Метрики (фаза 2): шесть метрик из журнала событий, Spring Batch, «недостаточно данных» при малой выборке, пояснения на дашборде.
- AI-менеджер (фаза 3): цикл инструментов, псевдонимизация имён, телефонов и идентификаторов, черновики действий с подтверждением владельца и валидацией движка, месячный бюджет токенов, журналы, экран диалога; ход в удалённом диалоге отвечает 409 `AI_CONVERSATION_ERASED` и ничего не отправляет провайдеру. Провайдер по умолчанию `stub`; адаптер DeepSeek есть.
- Эксплуатация: `docker-compose.prod.yml` (`app`, `web`, `keycloak`, две БД, `backup`), профиль `prod` с проверками секретов, бэкапы с проверенным восстановлением (`scripts/restore-drill.sh`), `scripts/deploy-smoke.sh` (8080/8081/8082 только loopback), CI (backend с гейтом JUnit ≥400; frontend; compose с проверкой `web`; docker; web; e2e).
- Тестирование этапа 08 (`docs/TEST_REPORT.md`): backend 1115 тестов, 0 failed, 0 skipped (сверено архитектором по JUnit XML; после полного прогона Java не менялся); Playwright 86 тестов: исполнитель 1 зелёный прогон, тестировщик 1 зелёный и 1 с падением AI-4 по таймауту под нагрузкой, после увеличения лимита `ai-drafts` 12 из 12 при трёх повторах; OIDC 11, 0 failed; `web-host-check.sh` PASS, 56 проверок, после исправления ошибки самой проверки; lint, `lint:selftest`, `i18n:check`, typecheck, web export зелёные.

## Что отложено (не входит в пилот)
- Фазы 4–7 плана по их критериям: живой Telegram-бот, напоминания и реактивация (есть порт канала, Trust, пакеты и stub с ручной задачей владельцу); сигналы роста с действиями; лендинг-витрина; полные каталоги ka/uk/cs (65 из 318 ключей, в OIDC скрыты, TD-66).
- Онбординг: `INSERT` в `tenant` и пользователь Keycloak с `tenant_id`, ролью и для мастера `specialist_id` — шаг оператора (README «First owner user»); каталог — владелец в консоли («Fill the catalog»). Привязки входа мастера к карточке в консоли нет: атрибут `specialist_id` в Keycloak или `keycloakUserId` через owner API.
- Нативные сборки iOS/Android (не собирались); измерение покрытия кода (JaCoCo нет, TD-70); версия строки в каталоге против lost update при втором OWNER (TD-74).

## Известные ограничения (открытый техдолг, `docs/tech-debt.md`)
- Удаление данных: вместе с диалогом AI удаляются и чужие черновики в нём; имя, не распознанное маской, и промпты, уже ушедшие настоящему провайдеру, не достаются (TD-79; со `stub` второго остатка нет); окно `refFor` при ходе чата одновременно с анонимизацией (TD-47); маскированный телефон в аудите `public.rate_limited` живёт 3 года (TD-80); гонка с завершением или переносом визита даёт одной стороне 409 `CONCURRENT_RETRY` без потери данных (TD-81); анонимизированные клиенты остаются в знаменателях `CHURN_RISK`/`REPEAT_RATE` (TD-32).
- Веб: CSP сервиса `web` держит `'unsafe-inline'` в `script-src`/`style-src` (TD-78); шрифты и иконки грузятся с Google Fonts (TD-67); правило 24-часового формата и `weekStartsOn` не действуют, дата и время в каталоге вводятся текстом (TD-65, TD-73); `datetime.ts` без юнит-тестов, DST и Hermes не проверены (TD-69); `useFocusEffect` в группе консоли проверен только на web (TD-62); диалоги переноса показывают плоский список слотов за 14 дней (TD-56).
- Публичная страница и консоль: выбор страны телефона на `/book` — только GE, RU, UA, CZ (TD-75); запасная валюта `GEL` в `money.ts`, пока профиль не загружен (TD-77); страница клиента `/b/{id}` берёт слоты из публичного маршрута с лимитом 5/мин на IP (остаток TD-76); 409 `CONCURRENT_RETRY` в календаре и на `/b/{id}` показывается текстом сервера на английском.
- Каталог: `publicVisible=false` не закрывает `/slots` и `POST /bookings` по известному id (TD-72); расписание не версионируется, прошлые знаменатели загрузки меняются при правке графика (TD-29); `schedule_exception` без ограничений в схеме (TD-31).
- Данные и метрики: дашборд только «месяц к дате» (TD-34); лаг пересчёта 1 минута, ночной пакет 03:15, в OIDC ручного пересчёта нет (TD-35, TD-66); знаки валют у `Intl` и Java расходятся по 17 валютам, недостижимо на GEL/CZK (TD-63).
- AI: маскирование имён best effort (TD-36, TD-37); формат tool calling DeepSeek подтверждается только живой проверкой (TD-41); бюджет задаёт оператор в БД (TD-42).
- Безопасность и платформа: нет проверки audience у JWT (TD-03); владелец схемы — суперпользователь (TD-05).
- Не выполнялось: `docker compose up` стека с сервисом `web` (в CI проверен `compose config`, образ — отдельно); вход через Keycloak под CSP на настоящем nginx (OIDC E2E идёт через `e2e-serve.mjs` без CSP); адрес за TLS; живой DeepSeek; native; `Mark completed`/`Mark no-show` в браузере не нажимаются (покрыты backend-тестами); правки после четвёртого круга ревью без отдельного ревью — diff этапа прочитан архитектором целиком, дефектов не найдено; скриншоты этапа 08 просмотрены выборочно.
