# Приёмка Cadence

Дата: 2026-10-31. Основа: коммит `a271e3b` (этап 06) и незакоммиченные правки этапа 07 (`docs/stages/07-catalog-editing.md`). Приёмка архитектора по политике, п. 4.3; заменяет версию после этапа 06. Объём — пилот с одним арендатором: веб-консоль и публичная запись; не весь план продукта (`docs/PRODUCT_PLAN.md`).

## Что реализовано и принято (этапы 01–07)
- Операционный срез (фазы 1A/1B плана): арендаторы с RLS, каталог услуг и мастеров с матрицей и графиком, движок записи (снапшоты, GiST-исключение, статусы), публичная запись `/book/{slug}` с `.ics` и ссылкой управления `/b/{id}?token=`, CRM из записи, роль MASTER без телефонов и денег, правила записи, светлая и тёмная темы, RU и EN, демо-сид (только вне профиля `prod`).
- Редактирование каталога из консоли (этап 07, TD-68 закрыт): услуги, мастера, матрица с переопределениями, недельный график, исключения; серверная валидация с кодами ошибок, аудит в `audit_log` без ПДн, цена в валюте арендатора по знакам `Intl`; удаления нет — только `active=false`/`publicVisible=false`; деактивированный мастер теряет консоль (403 `SPECIALIST_INACTIVE`), его визиты только отменяются. Ссылка клиента берёт слаг из ответа визита (TD-64 закрыт).
- Метрики (фаза 2): шесть метрик из журнала событий, Spring Batch, «недостаточно данных» при малой выборке, пояснения на дашборде.
- AI-менеджер (фаза 3): цикл инструментов, псевдонимизация имён, телефонов и идентификаторов, черновики действий с подтверждением владельца и валидацией движка, месячный бюджет токенов, журналы, экран диалога. Провайдер по умолчанию `stub`; адаптер DeepSeek есть.
- Эксплуатация: `docker-compose.prod.yml`, профиль `prod` с проверками секретов, бэкапы с проверенным восстановлением (`scripts/restore-drill.sh`), `scripts/deploy-smoke.sh`, CI (backend, frontend, compose, docker, e2e; гейт JUnit ≥400, 1075 на момент приёмки).
- Финальное тестирование (этапы 06–07, `docs/TEST_REPORT.md`): backend 1075 тестов, 0 failed, 0 skipped (архитектор сверил по JUnit XML); Playwright 78 тестов (E1–E7, E9, E10, unit-ввод каталога, AI-1…AI-8) дважды и 9 тестов OIDC (E8), 0 failed, 0 flaky (сверено по отчётам Playwright); lint, typecheck, i18n (en/ru 302/302), web export — зелёные по отчёту тестировщика, архитектором не перепроверялись. E10 выполнен в режиме dev-headers; формы каталога в OIDC не прогонялись.

## Что отложено (не входит в пилот)
- Фазы 4–7 плана по их критериям: живой Telegram-бот, напоминания и реактивация (есть порт канала, Trust, пакеты и stub с ручной задачей владельцу); сигналы роста с действиями; лендинг-витрина; полные каталоги ka/uk/cs (65 из 302 ключей, в OIDC скрыты, TD-66).
- Онбординг: `INSERT` в `tenant` и пользователь Keycloak с `tenant_id`, ролью и для мастера `specialist_id` — шаг оператора (README «First owner user»); услуги, мастера, матрица и график — владелец в консоли (README «Fill the catalog»). Привязки входа мастера к карточке в консоли нет: атрибут `specialist_id` в Keycloak или `keycloakUserId` через owner API.
- Маршрут удаления данных клиента (`CrmService.anonymize` без вызова, TD-46); нативные сборки iOS/Android (не собирались); измерение покрытия кода (JaCoCo нет, TD-70); версия строки в каталоге против lost update при втором OWNER (TD-74).

## Известные ограничения (открытый техдолг, `docs/tech-debt.md`)
- Веб: статический хост обязан переписывать `/book/*`, `/b/*`, `/clients/*`, `/specialists/*` на `[param].html`, иначе ссылка клиента даёт 404 (TD-57, HIGH); ошибка слотов, включая 429, показывается как «нет слотов» (TD-55); правило 24-часового формата и `weekStartsOn` не действуют, дата и время в каталоге вводятся текстом (TD-65, TD-73); шрифты и иконки грузятся с Google Fonts (TD-67); `datetime.ts` без юнит-тестов, DST и Hermes не проверены (TD-69); `useFocusEffect` в группе консоли проверен только на web (TD-62).
- Публичная страница и консоль: выбор страны телефона на `/book` — только GE, RU, UA, CZ (TD-75). Диалоги переноса в консоли ходят в публичный `/slots` с лимитом 5/мин на IP: владелец и клиенты за одним NAT делят лимит, за прокси без `APP_RATE_LIMIT_TRUSTED_PROXIES` все запросы — один IP (TD-76). Запасная валюта `GEL` в `src/utils/money.ts:2` достижима через карточку метрик, пока профиль не загружен (TD-77).
- Каталог: `publicVisible=false` не закрывает `/slots` и `POST /bookings` по известному id (TD-72); панель визита без снапшота цены (TD-71); расписание не версионируется, прошлые знаменатели загрузки меняются при правке графика (TD-29); `schedule_exception` без ограничений в схеме (TD-31).
- Данные и метрики: дашборд только «месяц к дате» (TD-34); лаг пересчёта 1 минута, ночной пакет 03:15, в OIDC ручного пересчёта нет (TD-35, TD-66); знаки валют у `Intl` и Java расходятся по 17 валютам, недостижимо на GEL/CZK (TD-63).
- AI: маскирование имён best effort (TD-36, TD-37); формат tool calling DeepSeek подтверждается только живой проверкой (TD-41); бюджет задаёт оператор в БД, без строки действует значение по умолчанию (TD-42).
- Безопасность и платформа: нет проверки audience у JWT (TD-03); владелец схемы — суперпользователь (TD-05); активность мастера проверяется запросом в БД на каждый вызов консоли.
- Не выполнялось: job `e2e` в GitHub Actions (только локально), живой DeepSeek, прод за TLS; `Mark completed`/`Mark no-show` в браузере не нажимаются (покрыты backend-тестами); последний круг правок этапа 07 (M1, m1–m7) без отдельного ревью — `TenantContextFilter`, репозиторий и сервис каталога, V16 и контроллер прочитаны архитектором, дефектов не найдено; скриншоты этапа 07 просмотрены выборочно: архитектор 9 из 24 файлов E10, координатор основные формы (`docs/TEST_REPORT.md`, раздел 8).

## Условия запуска пилота
Выполнено: семь этапов приняты; полное тестирование (п. 5 политики) пройдено; техдолг записан.
Блокирует запуск с реальными клиентами (шаги пользователя и оператора, приёмкой не проверялись):
1. Деплой за TLS по README «Production deployment»; веб-сборка с `EXPO_PUBLIC_API_URL` и `EXPO_PUBLIC_OIDC_ISSUER` (без них в сборке localhost); `scripts/deploy-smoke.sh --strict --check-ports` с реальным токеном — PASS; `kcadm.sh` для realm `master`; `APP_RATE_LIMIT_TRUSTED_PROXIES`.
2. Статический хост веб-консоли с правилами rewrite (TD-57) и ручная проверка `/book/<slug>` и `/b/<id>?token=` на реальном адресе, включая перенос по ссылке.
3. Офсайт-шифрованная копия бэкапов и `.env.prod`; `scripts/restore-drill.sh` на копии, возвращённой с офсайта; повторять ежемесячно и после миграций. V16 добавляет уникальный индекс привязки входа: на дублях миграция остановится и назовёт их.
4. Первый зелёный прогон CI на GitHub, включая job `e2e`; branch protection на обязательные job (без `e2e`, пока он не стабилен).
5. Онбординг: `tenant` и владелец по README «First owner user»; каталог — владелец в консоли по «Fill the catalog», до появления слотов на `/book/<slug>`; мастер — пользователь Keycloak с ролью MASTER и `specialist_id` карточки (id виден в URL `/specialists/<id>`).
6. AI: до живой проверки DeepSeek (README «Live check DeepSeek») и DPA с провайдером пилот идёт с `APP_AI_PROVIDER=stub` (экран AI — демонстрация). Реальный провайдер — только после обоих шагов.
7. Приватность: уведомление клиентам со сроками хранения, включая бэкапы (README «Backups and restore»), и договорённость с владельцем, как исполняются запросы на удаление данных до появления маршрута (TD-46).
Фаза 0 плана (валидация: интервью, кандидаты в пилот) не проводилась и остаётся шагом пользователя; приёмка её результат не проверяет.

## Вердикт
Этап 07 принят. Приложение в объёме пилота принято условно: код и тесты готовы, цель MVP №1 (владелец сам настраивает каталог и получает рабочую страницу записи) выполняется из консоли без оператора; запуск с реальными клиентами возможен после пунктов 1–7. По умолчанию пилот — веб-консоль и публичная запись одного арендатора с AI на `stub`; живой AI — отдельное решение после живой проверки и DPA.
