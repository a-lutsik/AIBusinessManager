## 1. Что это за проект

Cadence — AI-бизнес-менеджер для соло-мастеров и микро-команд (до 5 мастеров): публичная запись без аккаунта,
автоматический CRM, шесть метрик роста, объяснимый Trust, AI-ассистент с черновиками действий, Telegram как единственный канал.
Стек: Java 25 / Spring Boot 4.1, jOOQ + Flyway, TimescaleDB, Keycloak, Expo Router (RN Web). Модульный монолит из 9 Gradle-модулей.

Вся функциональность появилась одним коммитом `1347221` (190 файлов, ~19.8k строк) 2026-09-16, затем три коммита по дизайн-системе.
Документация: `PRODUCT_PLAN.md` (445 строк, подробный, без статуса выполнения) и README с самоотчётом «What is implemented» по фазам 1A–7.
Отсутствуют: `docs/stages/*`, `docs/tech-debt.md`, `docs/TEST_REPORT.md`, `docs/ACCEPTANCE.md`, ADR, CI-конфигурация.

## 3. Оценка реализации

### 3.1 Что сделано хорошо

- Архитектурный скелет соответствует плану: модули `api`/`internal`, ArchUnit запрещает JPA и доступ в `internal` соседей, `ai` не видит jOOQ-таблицы.
- Паттерны из §3.3 реально присутствуют: Strategy (`LlmProvider`, `NotificationChannel`), State (`AppointmentStatusMachine`), чистая функция `SlotCalculator`, снапшоты цены/длительности/буферов, Outbox с `FOR UPDATE SKIP LOCKED`, Factory токенов.
- Схема БД близка к плану: `tstzrange` generated-колонки, частичный GiST exclusion по занимающим статусам, hypertables только для временных рядов, outbox обычной таблицей, RLS-политики на всех доменных таблицах, `SET LOCAL` через `TransactionExecutionListener`.
- Opaque-токен брони: 256 бит, в БД SHA-256, срок жизни, отзыв, скоуп одного визита.
- `problem+json` с машинным кодом, DeepSeek-адаптер с нормальными тестами (ключ не утекает в ошибку, fail-fast без ключа).
- Код читаемый, классы небольшие, самый крупный `BookingServiceImpl` — 526 строк.

### 3.2 Критичные дефекты (блокируют любой пилот с реальными данными)

1. **Аутентификация фактически отсутствует.** `app.security.oauth2-enabled=false` по умолчанию, `appApiChain` делает `permitAll`, а `TenantContextFilter` доверяет заголовкам `X-Tenant-Id`, `X-Actor-Role`, `X-Specialist-Id`. Любой клиент становится владельцем любого арендатора. Фронтенд хранит роль в `localStorage` и шлёт её заголовком; OIDC-логина в Expo нет вообще. Даже при включённом OAuth2: без claim `roles` роль по умолчанию `OWNER` (`roleFromJwt`), без claim `tenant_id` берётся заголовок, без JWT и заголовков — `local-owner` OWNER. Тест «мастер не видит чужое» проверяет только header-роли.
2. **RLS не является жёстким барьером.** Миграции и приложение работают под одним пользователем `cadence`, который владеет таблицами; `FORCE ROW LEVEL SECURITY` не включён, отдельной роли приложения нет. Комментарий в V4 это признаёт. Косвенное доказательство: `AiAssistantServiceImpl.chat` нетранзакционный, `set_config` не вызывается, `ai_prompt_log` пишется — при работающем RLS WITH CHECK отклонил бы вставку. Аналогично `/api/public/bookings/{id}` (нет слага в пути → `TenantContext` пуст при `afterBegin`) и обработчики outbox.
3. **Сырой токен брони хранится в БД открытым текстом** в `owner_task.copy_text` и `owner_task.link` — противоречит §5 «в базе только хеш».
4. **`CrmService.merge` теряет данные:** «слияние» лишь анонимизирует поглощаемый профиль, визиты не перепривязываются к выжившему `client_id`.
5. **Rate limit доверяет `X-Forwarded-For`** без списка доверенных прокси → обходится одним заголовком. Из трёх лимитов плана реализован один (5/мин/IP на слоты) и один несуществующий в плане (20/час/IP на бронь); лимитов на телефон и на слаг нет; события 429 в audit не пишутся.

### 3.3 Существенные расхождения с планом (функция заявлена, но не работает)

- **AI-черновики — мёртвый код.** `saveDraft` никем не вызывается, `chat()` всегда возвращает `drafts = []`. Нет ни одного инструмента из §4.6 (`get_schedule`, `find_free_slots`, `draft_booking`...), нет structured output. Экран AI показывает карточки, которые не могут появиться. Confirm-ветка применяет только `draft_booking`, остальные типы молча «подтверждаются».
- **Псевдонимизация минимальна:** regex на телефон/email, имена → `hashCode` (коллизии), обратная карта в памяти JVM (теряется при рестарте, в истории диалога остаются токены). Нет маскирования заметок, стоп-слов, переключателя «не передавать заметки», лимитов токенов/стоимости.
- **Spring Batch декоративен:** `metricsJob` — один tasklet с циклом по всем арендаторам (нет chunk по `tenant_id`, restart, skip), и он не запускается (`spring.batch.job.enabled=false`); реальный пересчёт делает отдельный `@Scheduled`, минуя Job. **Spring Integration** — один `DirectChannel`, к которому никто не подключён.
- **Метрики считаются не из журнала событий**, а из текущего состояния `appointment` через `bookingService.calendar` (с N+1-обогащением). `appointment_event` пишется, но никем не читается; критерий фазы 2 «воспроизводимо из журнала событий» не выполняется по построению. Загрузка слотов игнорирует исключения графика (выходной считается доступным временем). Churn-fallback — хардкод 21 день вместо медианы арендатора.
- **Сигналы:** три захардкоженных правила; `LOW_VALUE_SERVICES` сравнивает с «4000 минорных единиц» независимо от валюты (для CZK-арендатора бессмысленно); сигналы дублируются при каждом ночном пересчёте без дедупликации.
- **Фаза 4 почти не начата:** нет напоминаний 24ч/2ч, реактивации, остановки сценариев при отзыве согласия; `deductSession` не вызывается при `COMPLETED`, флаг `deduct_package_on_no_show` не используется; `ManualTaskNotificationChannel` не является fallback при отсутствии `chat_id` (обработчик outbox шлёт только в telegram-заглушку). Override Trust не пишется в audit (план §4.4 требует).
- **Исправление NO_SHOW↔COMPLETED** ломает агрегаты CRM: `no_show_count`/`completed_visit_count`/`completed_value_minor` только инкрементируются и никогда не откатываются; отдельной audit-записи для исправления нет.
- **Гонка при создании визита** ловится GiST-констрейнтом, но `DataIntegrityViolationException` не маппится в `SLOT_OCCUPIED` → клиент получает 500 вместо 409.
- **Outbox poller:** обработчик и пометка `processed_at` в одной транзакции с чтением батча; если обработчик упал на SQL-ошибке, транзакция отменена, `attempts++` не применится, батч откатится и «ядовитое» событие заблокирует очередь (ORDER BY created_at LIMIT 25). Нет max attempts / dead letter.
- **N+1 в HTTP-потоке:** `enrich()` на каждый визит делает 4+ запроса (клиент, trust → клиент, правила, trust_state). `GET /api/app/clients/{id}` грузит все визиты арендатора с 2020 года, чтобы отфильтровать одного клиента; `GET /clients` для мастера — два года календаря.
- **Локализация:** `t()` — плоский lookup без ICU-плюрализации (`intl-messageformat` в зависимостях, не используется); бэкенд-каталоги `messages_*.properties` не читаются (тексты задач владельца захардкожены на английском); шрифты Inter/Plus Jakarta Sans без грузинского набора — `ka` даст квадраты (план требует Noto Sans). Каталоги ka/uk/cs покрывают 59 из 121 ключей.
- **OpenAPI** описывает 18 путей из 46 реальных эндпоинтов; TypeScript-клиент не генерируется, типы написаны вручную с `optionalRequest`, который глушит 404 и скрывает дрейф контракта.
- **Эксплуатация фазы 1A** отсутствует: нет CI, Dockerfile приложения, бэкапов, `request_id`, OTLP; actuator только health/info.
- Остатки Expo-шаблона (`(tabs)`, `modal.tsx`, `EditScreenInfo`, `two.tsx`), `AppApiController.me()` при отсутствии актора возвращает OWNER.

### 3.4 Тестовое покрытие

Юнит-тестов нет на: `MetricsCalculator` (ни одна из шести метрик), Trust-правила, CRM-агрегаты, `Pseudonymizer`, `OutboxPoller`, перенос/отмену, rate limit, статусы в `transition` (CRM-побочки). `BookingCoreIT`: 4 сценария, три из них с `assumeTrue` на наличие слотов → при неудачном сиде пройдут как «пропущены», а не упадут. Изоляция арендаторов проверяется чтением публичного профиля второго арендатора, а не попыткой утечки. Playwright отсутствует. ArchUnit не проверяет «нет jOOQ вне репозиториев» — `GrowthServiceImpl`, `RetentionServiceImpl`, каналы уведомлений ходят в `DSLContext` напрямую, что нарушает §2 и §3.1.

## 4. Приоритеты: что исправить, доделать, переделать

**Исправить до любого показа с реальными данными (P0)**
1. Включить OAuth2 по умолчанию; header-режим только под профилем `local-dev`; отсутствие claim `roles`/`tenant_id` → 401, не OWNER. OIDC-логин в Expo (expo-auth-session) и роль из токена, не из `localStorage`.
2. Отдельная DB-роль приложения без ownership таблиц или `FORCE ROW LEVEL SECURITY`; тест «запрос без tenant-контекста не возвращает строк». Все сервисы, пишущие в БД, — транзакционные.
3. Не хранить сырой токен в `owner_task`; выдавать ссылку один раз или хранить отдельно зашифрованной.
4. `merge` с перепривязкой визитов/пакетов/ledger; откат агрегатов при исправлении статуса.
5. Маппинг exclusion-violation → 409 `SLOT_OCCUPIED`; outbox: обработка в отдельной транзакции, лимит попыток.

**Доделать по плану (P1)**
- AI: structured output или function calling → реальные `draft_*`, иначе убрать карточки из UI и из README.
- Метрики: считать из `appointment_event` (или честно переписать §4.5 и критерий фазы 2), учитывать исключения графика, дедуплицировать сигналы, валюто-независимые пороги.
- Тесты на шесть метрик с рукотворными ожидаемыми значениями; тесты изоляции и per-resource для записи (не только чтения); убрать `assumeTrue` из golden path.
- Rate limits по плану (телефон, слаг), доверенные прокси, 429 в audit.
- CI (GitHub Actions): build, Flyway+codegen, ArchUnit, ITs, OpenAPI-контракт, lint фронтенда.
- Перегенерация OpenAPI из кода (springdoc) и TS-клиента; убрать `optionalRequest`.
- ICU-плюрализация, бэкенд-`MessageSource` для клиентских текстов, Noto Sans Georgian.

**Переделать или убрать (P2)**
- Spring Batch: либо настоящий chunk-oriented job с restart (и `@Scheduled` запускает Job), либо удалить зависимость и исправить план/README.
- Spring Integration: убрать до появления второго адаптера, как и предписывает §2.
- `enrich()` → один join-запрос; детальная карточка клиента через запрос по `client_id`.
- Удалить остатки Expo-шаблона.

## 5. Адверсальное ревью плана и документации

**Тезис 1. План не содержит механизма проверки собственного выполнения.** В 445 строках нет ни одного статуса, даты, владельца или ссылки на доказательство. Чеклист экранов (§6) — 15 пустых чекбоксов. Единственный источник статуса — README-самоотчёт, написанный тем же агентом, что писал код, и он завышает: «Spring Batch metrics job», «Spring Integration channel seam», «draft confirm via Booking Engine», «pseudonymization» при фактическом состоянии из §3.3. Глобальная политика проекта требует `docs/stages/NN.md`, приёмку этапа и `docs/TEST_REPORT.md` — ничего из этого нет, значит формально ни один этап не закрыт.

**Тезис 2. Фаза 0 пропущена, а на ней держится всё остальное.** План сам говорит: «смысл фазы — не начать очень хорошо реализовывать то, что никому не нужно», критерий — письменная фиксация, за что готовы платить, и 2–3 кандидата в пилот. Вместо этого за один день реализованы фазы 1A–7 «на уровне скелета». Нет ни одного артефакта интервью, гипотезы ценности или waitlist-бэкенда (форма пишет в `localStorage`). Самый большой риск проекта сейчас не технический.

**Тезис 3. План переопределён технологически и недоопределён продуктово.** Жёстко зафиксированы Java 25, Spring Boot 4.1.x, TimescaleDB, Spring Batch и Integration «по задаче», шесть паттернов — но нет ни одного user story с acceptance-критерием, ни одного экрана с состояниями, ни SLA/объёмов (сколько визитов у арендатора, сколько арендаторов на VPS). Следствие видно в коде: архитектура воспроизведена аккуратно, продуктовая логика (сценарии ретеншена, инструменты AI, пакеты) — заглушками.

**Тезис 4. TimescaleDB не оправдан нагрузкой.** Микро-команда до 5 мастеров генерирует порядка 200–500 событий в месяц. Hypertables для `audit_log`, `appointment_event`, `metric_snapshot` при таких объёмах дают только сложность: составные PK `(id, created_at)`, невозможность FK на эти таблицы, сложности с jOOQ codegen (отсюда «портативный» `schema.sql`-дубликат схемы и naive `TIMESTAMP` вместо `timestamptz` вопреки §4.2). Vanilla Postgres с партиционированием «когда понадобится» был бы честнее относительно принципа «никаких преждевременных решений».

**Тезис 5. Запрет на интеграции противоречит рынку, на который целится план.** Целевые локали — RU/GE/UA/CZ, где у салонов уже стоят Altegio/YClients/Booksy. Для них «запись» без импорта базы и без синхронизации с внешним календарём — это вторая система учёта, а не замена. План относит это за фазу 7, то есть после всех фаз, но именно это определяет, будут ли метрики фазы 2 считаться на реальных данных или на пустой базе нового арендатора. Как минимум импорт клиентов/истории (CSV) должен быть в 1B.

**Тезис 6. Telegram как единственный канал — слабое допущение для GE/CZ.** В Грузии и Чехии доминируют WhatsApp/Viber/SMS; у многих клиентов салонов Telegram нет, и тогда «fallback — задача владельцу на ручную отправку» становится основным режимом, то есть продукт возвращает владельцу ту переписку, которую обещал убрать. План должен либо допустить SMS-провайдера в MVP, либо измерить долю клиентов с Telegram на фазе 0.

**Тезис 7. Безопасность публичной записи недооценена.** Телефон без OTP + создание профиля клиента = любой может создать 40 клиентов с чужими номерами и испортить Trust/метрики; защита только rate limit (который в коде обходится заголовком). План признаёт риск, но не описывает ни капчу, ни верификацию по звонку/коду при первой записи, ни процедуру чистки спам-профилей. GDPR-раздел описывает сроки хранения, но ни одна политика ретенции не реализована, и в плане нет задачи на их реализацию ни в одной фазе.

**Тезис 8. «AI-первый» продукт откладывает AI на фазу 3 без MVP-критерия для него.** Критерий фазы 3 — «ассистент объясняет ситуацию цифрами и предлагает действия» — не измерим (нет набора эталонных вопросов и ожидаемых ответов, нет лимита стоимости на арендатора, нет политики провайдера для ЕС-данных, хотя §10 требует обработку в ЕС, а выбран DeepSeek). При этом ценностное предложение лендинга строится на AI.

**Тезис 9. Деньги исключены, но «выручка» вынесена в метрику.** Метрика «стоимость выполненных услуг на час» без `amount_received` и без скидок/пакетов на практике совпадёт с прайсом, и владелец быстро обнаружит, что дашборд не отражает кассу. План честно оговаривает терминологию в UI, но не объясняет, зачем тогда метрика нужна владельцу на этапе принятия решения о покупке.

**Тезис 10. Критерии готовности фаз неверифицируемы в текущем виде.** «Продукт можно показывать без извинений за интерфейс» (1B), «снижение no-show измеряется на пилотных салонах» (4) — без базовой линии, выборки и срока. Для фазы 1A критерий E2E Playwright не реализован, и README переводит его в «BookingCoreIT покрывает golden path», что подменяет критерий.

**Что изменить в документации**
- Добавить в `PRODUCT_PLAN.md` таблицу статуса фаз с ссылками на доказательства (тесты, скриншоты, отчёты) и завести `docs/stages/*`, `docs/tech-debt.md` по политике.
- Переписать README «What is implemented» в формате «сделано / заглушка / не начато» по каждому пункту; текущий раздел «Gaps (honest)» занижает разрыв.
- Вернуть фазу 0 как первую задачу: интервью, доля клиентов с Telegram, наличие Altegio/аналогов, готовность платить.
- Пересмотреть §2 «зафиксированные решения»: TimescaleDB, Batch/Integration и запрет импорта — кандидаты на отмену или перенос.
